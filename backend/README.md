# backend

FastAPI service behind the True Gym app: accounts, personal records and body
weight. Python 3.12, SQLAlchemy 2 (async, asyncpg), Alembic, Postgres 16.

## Running it

Copy the environment file and fill it in. `DATABASE_URL` and `JWT_SECRET` are
the two that matter; `PGUSER` and `PGPASSWORD` must match the credentials inside
that URL, because Docker creates the database role from them.

```
cp .env.example .env
openssl rand -base64 32     # paste as JWT_SECRET
```

Nothing here may be prefixed `EXPO_PUBLIC_`. Expo inlines any variable with that
prefix into the mobile JS bundle in cleartext, so these values are server-only.
No value may contain `$` either: compose reads this file for interpolation, so a
`$U` inside a key silently becomes an empty string, and the container ends up
holding a different secret than a local run does.

Then, with Docker:

```
docker compose up --build
```

That starts Postgres in the `true_gym_data` volume, applies migrations and
serves the API on port 8000. `docker compose down` keeps the data; only
`down -v` destroys it.

Or against a Postgres you run yourself:

```
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/alembic upgrade head
.venv/bin/uvicorn app.main:app --reload
```

Both read the same `DATABASE_URL`. The compose database publishes 5432 on the
host precisely so one URL works either way — which also means **nothing else may
hold 5432**. A system Postgres cluster, or `gym_tg_bot`'s container, will take it
first and this stack won't start. Stop those before bringing it up.

The API binds every interface, so a phone running Expo Go reaches it at
`http://<this machine>:8000`. Interactive docs are at `/docs`.

## Migrations

```
.venv/bin/alembic revision -m "what changed"   # then write the upgrade by hand
.venv/bin/alembic upgrade head
```

Migrations are hand-written rather than autogenerated: two indexes are
functional (`lower(username)`, `lower(exercise)`) and autogenerate does not
round-trip those faithfully. The container runs `upgrade head` before uvicorn,
so an image and the schema it expects arrive together.

## Endpoints

Everything except `/auth/*` and `/health` needs
`Authorization: Bearer <access token>`.

| Method | Path | Notes |
| --- | --- | --- |
| POST | `/auth/signup` | username, email, password, and optionally height, weight and goal weight → user + tokens |
| POST | `/auth/login` | email + password → user + tokens |
| POST | `/auth/refresh` | trades a refresh token for a new pair |
| POST | `/auth/logout` | ends the session that token belongs to |
| GET | `/auth/me` | the signed-in account |
| GET | `/prs` | records, newest created first |
| POST | `/prs` | idempotent by exercise — saving an existing one replaces its weight |
| DELETE | `/prs/{id}` | |
| GET | `/weights` | entries, newest first |
| POST | `/weights` | append a reading |
| GET | `/weights/stats` | latest, deltas, 7/30-day averages, trend |
| DELETE | `/weights/{id}` | |
| GET | `/pings/received` | invitations to this user |
| GET | `/pings/sent` | invitations this user sent |
| POST | `/pings` | invite a username to train at a time |
| PATCH | `/pings/{id}` | accept or decline; recipient only |
| DELETE | `/pings/{id}` | withdraw an invitation; sender only |
| PATCH | `/account/profile` | height, goal weight and avatar; no password needed |
| PATCH | `/account/email` | needs the current password |
| PATCH | `/account/username` | needs the current password |
| PATCH | `/account/password` | ends every other session, returns a new pair |
| DELETE | `/account` | takes records, weights and sessions with it |
| GET | `/health` | |

## Conventions

**JSON is camelCase.** The client is JavaScript, so it reads `accessToken` and
`updatedAt`. Requests accept either spelling.

**Errors are always `{"detail": "one sentence"}`**, validation failures
included, because the app renders that string straight into a form's error line.
A wrong password on an account screen answers `403`, not `401` — a client that
treats 401 as "the session expired" would log the user out over a typo.

**Sessions.** The app has no "remember me" checkbox, so every login is
remembered: a 30-minute access token alongside a refresh token good for 90 days,
rotated on each use and stored only as a SHA-256. Rotation leaves the spent row
revoked, and a revoked token coming back means one was spent twice — that ends
every session for the account. Logging out and changing a password *delete*
rows instead, so an ordinary retry is never mistaken for that.

**Body metrics.** Height and goal weight live on the account — one current
value each, changed rarely. A starting weight does not: it is a reading like any
other, so signup writes it into the weight log, and the trend series begins the
day the user joined. All three are optional, so a skipped signup screen still
leaves a usable account, and `PATCH /account/profile` fills them in later. On
that route an omitted field keeps its value while an explicit `null` clears it —
otherwise a screen editing only the goal would wipe the height every save.

**Avatars** are a Postgres enum, `avatar_key`, holding the nine keys in
`mobile/src/avatars.js`. Only the key is stored: the artwork ships inside the
app, so redrawing an avatar never touches the database, and a key the client
doesn't know would render as nothing — which is why the column refuses one.
Adding a tenth is `ALTER TYPE avatar_key ADD VALUE` in a migration, and the two
lists have to be changed together.

**Pings** are one row, not one per side: the sender reads it as sent and the
recipient as received, and `user` in the response is always the other person, so
the same row renders as "to @sam" in one tab and "from @alex" in the other. The
time is truncated to the minute, and `unique (from_user_id, to_user_id, at)`
stops the same invitation being sent twice — as a constraint rather than a
check, since a check-then-insert races exactly when someone holds the button
down. Only the recipient can answer, only the sender can withdraw, and a ping
that isn't yours reports 404 rather than 403.

**Layout.** `routers/` handle HTTP and nothing else. `services/` hold the domain
logic and raise the errors in `errors.py`, which `main.py` maps to status codes.
`models.py` is the schema and `schemas.py` the wire format; they differ where it
matters — `weight_kg` is a `Decimal` column, `weight` is a number in JSON.
